# Monorepo结构迁移实施计划

日期：2026-10-09。本文为待实施计划，只定义目标结构、迁移顺序、路径契约与验收；本轮不移动源码、模型、运行状态或既有证据，不执行数据库操作。管理员业务能力另按[管理员登录与全能力管理实施计划](2026-10-09-管理员登录与全能力管理实施计划.md)实施。

## 1. 已确定的结构与边界

1. `enterprise_gateway/.git`保持唯一Git根，不创建嵌套仓库，不把父目录的项目过程材料迁入Git。
2. 后端整体归入`apps/backend`。Python仍只有一个`enterprise-privacy-gateway`包，gateway和knowledge-worker共享源码、依赖与镜像，运行时为不同进程；不改包名、Python import或新增uv workspace。
3. 管理前端使用独立`apps/admin-web`工程：React、TypeScript、Vite、Ant Design，沿用管理员计划的React Router和TanStack Query职责划分。
4. 根`package.json`设置`private: true`，npm workspaces只包含`apps/admin-web`。唯一`package-lock.json`和`.node-version`位于Git根，前端子目录不建立另一份lock。根不创建`pyproject.toml`。
5. 根`contracts/admin.openapi.json`由后端导出，前端据此生成`apps/admin-web/src/api/schema.d.ts`。API契约与生成类型不手工维护两份定义。
6. Compose归入`deploy/compose.yaml`，Nginx配置归入`deploy/nginx/admin.conf`。前后端独立构建和部署，由同源入口代理管理API。
7. 仓库技术`docs`保留Git根。父目录的过程`docs`、WBS、执行证据与接续材料保留原位置；本文件跟踪于仓库`docs/`，仅作结构迁移实施计划，不记录工单进度、任务编号或运行证据。
8. 不创建`packages/`或空共享库，不引入Nx/Turbo，不增加旧路径转发脚本、软链接、兼容环境变量或fallback。
9. 目录迁移与管理员业务改造分别验收。M1不删除旧历史业务实现、不宣称登录完成；旧`web`彻底删除、React页面重写和新认证贯通由业务B1完成。

## 2. 当前依据与成熟模式

本轮核对的是现有配置、构建文件、脚本清单及Git模型跟踪状态，不以历史聊天中的测试通过作为迁移基线。迁移前事实如下（链接已指向迁移后位置）。

| 当前依据 | 迁移影响 |
|---|---|
| [pyproject.toml](../apps/backend/pyproject.toml)通过Hatch列出`src/audit`等包目录 | 后端项目根变为`apps/backend`，包内布局和import保持不变 |
| [uv.lock](../apps/backend/uv.lock)、[.python-version](../apps/backend/.python-version)和[运行依赖导出](../apps/backend/requirements-runtime.txt)迁移前位于仓库根 | 三者随Python项目移动，不能在仓库根新增第二个Python项目 |
| [后端check](../apps/backend/scripts/check.ps1)按脚本父目录确定cwd，执行frozen/offline安装和unittest | 整体移入backend后继续只验证后端，新增根聚合check另行实现 |
| [Dockerfile](../apps/backend/Dockerfile)使用`/app/src`并显式`COPY models/` | 后端context改变，容器内部路径可以保持；模型必须成为明确准备的构建输入 |
| [compose.yaml](../deploy/compose.yaml)迁移前context和providers挂载使用`.`、`./config` | 移至deploy后相对路径基点改变，必须整体校正构建、bind mount及secret路径 |
| [.dockerignore](../apps/backend/.dockerignore)隔离运行状态与秘密；[.gitignore](../.gitignore)忽略models等资产 | backend ignore随项目移动，根Git ignore扩展前端产物；前端根context另设白名单 |
| `git ls-files models`没有结果，当前models整体被Git忽略 | 模型不是tracked源码，禁止批量git mv；现有磁盘资产不能因目录清理而丢失 |

采用已验证的单Git仓库、多应用目录和各语言原生依赖管理模式；目录名称是本项目选择，不要求套用额外构建平台。

| 官方来源 | 本计划采用范围 |
|---|---|
| [npm workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/) | 根声明唯一前端workspace，根安装与workspace命令，统一Node依赖图 |

| [Compose多文件路径规则](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/)及[项目名](https://docs.docker.com/compose/how-tos/project-name/) | 以指定Compose文件确定路径，显式绑定项目与实际持久卷，不依赖旧cwd |

npm workspaces、uv workspaces和Docker context资料在本轮只读查阅。其余为实施时进一步核对的官方入口；具体Node/npm、前端依赖和镜像版本在M0核对兼容性后固定，不使用`latest`作为复现标识。

## 6. Node、Python和API契约

### 6.1 安装与检查入口

根只承担npm workspace和聚合检查。Node兼容版本由M0核实后写入`.node-version`及package声明，根lock按该环境生成并提交。前端依赖位于子工程package，根package不承载业务组件。

backend的check沿用已有frozen/offline、no-editable安装及真实unittest门禁。新根check具有独立职责：检查结构/工具版本 → 调用backend check → 从根`npm ci` → workspace类型/lint/测试/build及契约一致性检查；任一失败返回非零，不用`--if-present`跳过必要脚本。不把全部验证搬进Python项目，也不以旧check壳转发代替结构修正。

后端`.venv`在新项目根重新创建，不搬旧虚拟环境。离线依赖不足时保存失败；只能在授权网络条件下补齐后复验，不能用旧环境替代锁定安装通过。

### 6.2 管理OpenAPI

- 新工具位于`apps/backend/scripts/export_admin_openapi.py`，从实际FastAPI管理路由注册导出根`contracts/admin.openapi.json`。导出不启动外发、不读取真实PG正文，也不能因缺真实秘密删除路由。
- 文档/契约用无副作用的app构建路径，生产运行仍按真实资源装配并保持未就绪拒绝；不添加另一套虚假API。
- 导出包含实际`/api/admin/*`及引用schema，operationId稳定；JSON序列化排序和输出顺序确定，不带时间戳、机器绝对路径或秘密。
- 提供`--check`模式：在内存重新生成并与目标内容比较，漂移返回非零；不覆盖文件来消除失败。
- 前端脚本`generate:api`从根契约生成`src/api/schema.d.ts`；`check:api`比较实际生成结果与已提交文件，不手改generated类型。
- 两个文件有唯一生成来源，后端变更须同步更新契约与类型并跑编译。前端请求使用薄客户端管理Cookie/CSRF/错误，保留现有JSON语义，不新增通用响应包装框架。
- 管理B1实际路由未完成前，不提交空的“全部管理API”快照或手写schema冒充已导出能力。M2工具可用明确合成fixture验证，但真实契约交付与B1对齐，M3不能跳过这项前置。

## 7. 构建与模型准备契约

### 7.1 后端制品

后端Docker build context固定为`apps/backend`；使用其中的Dockerfile及`.dockerignore`，不COPY父目录技术docs、前端或过程证据。gateway与worker继续同镜像、不同command与受限凭据，不能因monorepo给worker管理员权限。

当前Dockerfile需要`models/`作为COPY源。未来模型准备需明确选择并验收：本计划的默认Compose制品路径为在backend context内专门准备`models/<制品>`，保持容器`/app/models/<制品>`；这只是构建输入，不提交Git。准备工具或操作须指定可信模型源、许可/manifest、文件hash和目标绝对路径，核对源与目标后才可构建。缺模型不生成空目录骗过构建或readiness。

如果实际部署已采用外部只读模型目录，则保持受控外部绝对路径并显式挂载/配置；未来执行时统一选择该部署的唯一绑定方式，删除不适用COPY或挂载规则，不增加“先内置再找外部”的fallback。模型改用外部资产不改变NER验包及检测质量验收。

本轮不复制、移动、下载、删除现有模型，也不以完整构建context发送未经清点的秘密和运行数据。

### 7.2 前端制品

前端Docker build context为Git根，以便读取唯一根lock和`deploy/nginx/admin.conf`。`apps/admin-web/Dockerfile.dockerignore`采用默认排除、精确允许：根package/lock/Node版本、必要前端源码和构建配置、根OpenAPI及指定Nginx配置。逐路径允许父目录和所需文件，不能以整仓`COPY . .`扩宽范围。

必须排除backend、`.git`、任意models、秘密、`.env*`、PG/runtime/state/evidence/reports、虚拟环境、cache、node_modules、dist/build和父目录过程材料；对未知新文件默认不进入context。Dockerfile专用ignore的实际效力用context检查及最终镜像抽查证明，不能只根据文件名判断安全。

多阶段构建从根`npm ci`，针对admin-web构建；运行镜像仅含必要静态dist和Nginx配置，不能包含源码树、Node构建依赖、OpenAPI导出工具或后端秘密。wheel不打包React页面，前端dist不打包Python包。

### 7.3 Compose路径

以`deploy/compose.yaml`为第一Compose文件，内部后端context为`../apps/backend`，前端context为`..`、dockerfile为`apps/admin-web/Dockerfile`。providers示例路径改为`../apps/backend/config/providers.json`。Operator、模型、秘密和PG连接使用明确的受控绝对路径或显式named volume，不依赖调用者原cwd。

Compose服务唯一命名为`frontend`、`backend`和`knowledge-worker`。worker使用与backend相同镜像，不设置独立Python包；frontend反代固定backend服务名，更新相关depends_on与内部探针。容器内部state、operator和已选择的模型路径按部署契约固定；迁移Compose文件不重建或清空原持久卷。明确Compose project name及既有`gateway-state`实际卷名，以避免仅因文件位置或服务名称改变创建新的空卷；切换前列出实际卷/secret/模型映射和数据范围。`compose config`、只读状态检查及实际启动后readiness共同验证；静态YAML解析不能代替运行。

## 8. 原生Windows与Compose部署分别验收

### 8.1 原生Windows

后端从`apps/backend`运行，显式设置可信分类器、operator、模型、state、KMS及PG绑定。新`.venv`按新cwd重建，不能继续引用旧根解释器。原有外部绝对资产路径可以保持，必须实际检查权限、manifest与readiness。

开发联调使用Vite服务：浏览器通过Vite单一origin访问页面及代理`/api/admin/*`和需要验证的`/v1/*`，后端独立端口；Cookie/Origin/CSRF按可观察路径验证。该模式标为开发验证，不使用`vite preview`声称生产静态服务已部署。

Windows生产运行需要明确可用的静态/反向代理服务。本计划不假设机器已安装Nginx；未来执行时准备并固定可验证的服务、配置与进程管理方式，再验证生产dist同源管理API、SPA刷新和退出。未准备好时只交付后端原生及前端开发验证，Windows生产静态托管保留未验收，不静默改为FastAPI内嵌页面。

### 8.2 Compose

通过独立frontend Nginx服务部署生产dist，管理`/api/admin/*`与模型`/v1/*`反代到固定backend服务。`/login`和`/admin/*`是前端路由，刷新支持SPA fallback；`/api/*`错误不得返回HTML壳，旧`/history`明确无入口。模型`/v1`仍按既有网络边界和BYOK保护，内部health/readiness不在公共SPA入口发布。

外部同源入口保持Cookie、Origin/CSRF及请求ID语义；后端不盲信客户端转发头。HTTPS入口应使用受控代理配置并正确确定Cookie Secure，HTTP保持用户已确定的显式传输选择，证书失败不降级。不存在将管理Cookie传给供应商的路径。

生产静态托管执行CSP、no-store、nosniff、防嵌入和敏感错误净化；Ant Design样式策略与管理员计划一致。正文只按React纯文本呈现，不用`dangerouslySetInnerHTML`解释模型内容。

## 12. 切换、失败处置和回退

1. 切换前记录当前已验证版本、tracked文件、依赖、模型manifest、实际卷/state/数据库范围及运行进程；不把目录移动当作数据搬迁。
2. 在新结构构建并验证后端及前端独立制品，生成组合清单，绑定后端镜像/wheel、前端镜像/dist、OpenAPI版本、部署配置与模型版本。
3. 新结构运行失败先定位cwd、模型/卷、构建context、代理或契约，保留真实错误后修正复验；不能加旧路径兼容脚本、软链接或双路由绕过失败。
4. 活动请求和持久作业仍按管理员计划及现有不可变版本契约处理。替换目录不改变在途请求、事务Spool提交或worker幂等语义。
5. 服务回退仅使用已验证的、匹配新结构及当前管理架构的完整制品和配置；没有可用匹配包时停止受影响服务，保留原运行资产。不能重新开启旧Key、旧双人接口、旧cwd探测或原文外发fallback。
6. 本轮及未来M1不删除原模型、秘密、PG角色/schema、卷、KMS或备份；专门资产准备若涉及复制/移动，先核对实际绝对目标和来源、hash与权限，再按明确范围执行。
