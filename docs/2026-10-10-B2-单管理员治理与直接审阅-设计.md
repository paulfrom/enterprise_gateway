# B2 单管理员治理与直接审阅 — 设计文档

日期：2026-10-10。前置：B0（契约基线 #3）、B1（登录与历史贯通 #4）已合并。
上游依据：`docs/2026-10-09-管理员登录与全能力管理实施计划.md` §12 B2 行、§12.1 文件所有权、`docs/contracts/admin-console.md`、`docs/contracts/admin-record-review.md`、ADR 0007。
本文是 B2 批次的实施设计；正式任务书与 WBS 登记由 root 在开工时建立。

## 0. 已裁决的边界问题

1. **纯后端批次**：B2 不触碰 `web/**`，管理页面全覆盖归 B4。纵切为真实 PG + HTTP/TestClient 级。
2. **record_review.py 整文件删除**：`audit/record_review.py` 与 `tests/audit/test_record_review.py` 删除，直接审阅由 `audit/admin_reader.py` 全新实现。计划 §10.2.3「不删除旧审批文件」仅指数据库对象与数据，Python 模块不属于该豁免。
3. **审计目录用文件存储**：可信审计目录为 durable_commit 文件目录，audit 保持零新增 PG 依赖；目录在既有留证成功后由受控后台流程构建，不增加出口同步写入门禁。
4. **五任务纵切**：T1 DDL/存储 → T2 治理服务 → T3 audit reader → T4 管理 API 整合 → T5 集成纵切。
5. **范围裁剪与复用归属**：`publications/export`、`dictionary/compile`、`retention`、`maintenance`、`jobs` 契约路由不属于 B2，统一归 B3；B3 治理负责人实现导出/词典服务，配置与运行负责人负责作业及保护包发布，认证/装配负责人整合路由。B2 冻结可用性与消费状态契约，并以真实 PG 验证已有导出/词典服务对新治理模型的兼容性；B4 实现对应页面。B3 的复用纵切是 B4 对应页面验收的前置，不再留待未定批次。
6. **脱敏优先与新增能力隔离**：治理、目录、消费与管理读取不得成为模型请求的新准入条件，不新增在线 PG 查询、治理等待或目录同步落盘。既有必需加密留证、历史持久化和 REQUIRED spool 门禁保持；这些既有资源失败仍按原契约拒绝请求。将采集改为非阻塞需另行修订采集契约，本批次不静默绕过。

## 1. 数据层：DDL v2

同一配置 namespace，替换式新结构；不写 migration，不对旧 schema 自动 ALTER/DROP，不搬运数据。

### 1.1 删除的旧双人构件

- `knowledge_approvals` 表（角色 CHECK）、`enforce_reviewer_identity` 触发器
- `enforce_publication_admission` 的 `approval_count<>2` 人数准入（触发器位置保留，语义重写，见 1.3）
- `save_approval` 及发布前置审批数复查、reject 的角色检查

### 1.2 新增/改造对象

| 对象 | 变更 | 契约要点 |
|---|---|---|
| `knowledge_admin_actions` | 新增 | 单管理员验证/动作记录。列：admin_action_id(uuid pk)、tenant_id、domain、actor_id（服务端固定 admin）、session_digest（会话关联摘要）、action_type（CHECK 枚举：governance_confirm/publish/reject/revise/withdraw/revoke）、object_type+object_id、object_version、rationale（依据）、intended_use、consumer_audiences(text[])、result(succeeded/failed)、created_at。承载主体、范围、对象版本、动作、用途、受众、依据、时间和结果；审计正文读取事件独立存文件，不依赖本表 |
| `knowledge_governance_versions` | 新增 | 来源治理版本。列：governance_version_id(uuid pk)、tenant_id、domain、source_id+source_version、admin_action_id FK、ownership/confirmed 归属、intended_use、consumer_audiences、valid_from、valid_until、rationale、supersedes_version_id、created_at。确认产生新版本；sources 原始行（原文/证据/原始 ACL/unverified 可信度）**不原位改写**；期限不得超过实际来源保留期限 |
| `knowledge_publications` | 改造 | publish 事务 INSERT 绑 admin_action_id、candidate_id+candidate_version、发布用途、消费受众与有效期限；不使用单个治理版本代表多来源候选 |
| `knowledge_publication_sources` | 新增 | 每个 publication 绑定全部贡献来源的 tenant/domain/source_id/source_version/governance_version_id；复合外键保证治理版本确属该来源与范围，唯一约束防重复，准入检查防遗漏 |
| `knowledge_candidates` | 改造 | 显式 candidate_version 与 derived_from；修订生成新记录，发布引用精确版本；同一候选版本失效后允许显式创建新 publication，幂等键仅去重同一次发布请求 |
| `knowledge_consumer_assets`、`consumer_receipts`、`knowledge_outbox` | 扩展 | 支持 §3.2 的真实资产标识/版本/类型、用途、谱系、应用与失效回执及投递结果；有效性仍由权威来源/治理/发布状态判定，receipt 不代替授权。B2 持久化授权导出/编译测试产生的资产谱系，B3 复用相同存储契约 |
| `invalidate_knowledge_source`（SECURITY DEFINER） | 保留并适配 | 撤回级联：tombstone+outbox、consumer_assets 失效；原始 ACL 保留作为证据，withdrawn 与有效授权判定阻止后续消费 |
| `read_authorized_knowledge_candidate`（SECURITY DEFINER） | 改造授权依据 | 保留逐行授权、来源锁与事务边界；处理读取使用原始处理 ACL，消费读取使用发布绑定的有效治理授权，验证全部来源与发布范围，不接受消费者自报角色升级 |
| 全表 RLS | 保留 ENABLE+FORCE | 策略分身份分支，见 §2 |

### 1.3 发布准入触发器（重写）

`enforce_publication_admission` 新语义：同一事务内存在匹配的 `knowledge_admin_actions` 行（action_type='publish'、object 指向该候选及版本、范围匹配、result='succeeded'），全部贡献来源未失效且各自当前治理版本有效，发布用途、受众和期限满足 §3.1。来源关联与 publication/outbox 同事务写入，使用提交前约束校验完整关联，不能在仅有 publication 行时提前认定准入成功。锁定候选及全部来源/当前治理版本，锁顺序固定，防止发布与撤回、重新治理并发穿透。人数检查彻底删除；失败不得伪造已发布。

### 1.4 结构指纹与旧 schema 拒绝

- `SCHEMA_FINGERPRINT_V2` 代码常量：对 schema 内表/列/函数/触发器/策略的 pg 元数据做规范化 canonical JSON 后 sha256；不对 DDL 文本哈希（避免格式脆弱）。T1 首次实现时由真实计算产生并内嵌，随后任何结构变更必须同步更新常量。
- 管理连接与 knowledge worker 启动均校验指纹；不匹配 → 固定净化错误 `KNOWLEDGE_SCHEMA_INCOMPATIBLE`，管理能力拒绝、worker 拒跑；零自动修复、零数据变更。旧 v1 实例保持原样独立运行。
- 初始化器 `scripts/prepare_knowledge_database.py` 延续「拒绝已存在 namespace」；事务内建 schema + v2 DDL + 管理/worker/consumer 最小角色授权 + 回读校验（forced RLS、非属主、无 SET ROLE 路径、表/函数/触发器/策略全契约——不能仅检查固定 13 张表）。指纹规范化剔除 OID、实例角色名与 schema 名等部署差异，保留函数体、约束、策略与权限的语义；用两个随机 schema/角色部署验证一致性。

## 2. 管理连接与 RLS 模型

契约要求管理 RLS 分支绑定**专用管理数据库身份**；history 侧运行时的单连接三 GUC 模式不满足，B2 新建双连接模型：

- **管理连接**：gateway 进程内为管理 API 建立第二条 PG 连接。新 secret `GATEWAY_ADMIN_KNOWLEDGE_PG_DSN(_FILE)`（exactly-one，镜像 `_history_spec` 校验模式），DSN 的 `search_path` 绑定 knowledge schema，连接角色 = 专用受限管理角色（非 owner、非 superuser、非 BYPASSRLS）。
- **AdminContext 注入**：每事务 `SET LOCAL app.tenant`、`app.domain` 与 `app.admin_context='true'`（归属现有 `app.*` GUC 家族，与 `app.subject`/`app.roles`/`app.subjects`/`app.purposes` 一致，管理策略与消费者策略读同一组 GUC）；值由服务端从有效管理会话的 AdminContext 注入，**不接受任何请求参数**。普通 SQL 的 `current_user` 为连接角色；SECURITY DEFINER 内会变为函数属主，相关函数必须验证受信连接身份（专用登录连接的 `session_user`）与服务端范围，不能把函数属主当管理员。worker/consumer 即使设置相同 GUC 也不能进入管理分支——管理策略同时校验 `current_user = 管理角色`，而 worker/consumer 连接角色不同且不可 SET ROLE（反例测试证明）。
- **管理策略**：`current_user = 管理角色 AND admin_context AND tenant/domain 匹配部署`。管理读取**不看消费者 active publication 过滤、不看来源 ACL**（admin 可查受限/拒绝/撤回/到期元数据）；正文释放走服务端解密路径，守实际保留与密钥状态，SQL 层不放开密文直读。
- **部署门禁**：prepare 回读 `pg_auth_members` 证明 worker/consumer 角色无到达管理角色的成员路径；`database_security.py` 扩展对应断言供 worker 启动复检。

## 3. 治理服务 v2（`knowledge/governance.py` 重写）

每个成功动作 = 一条事务：INSERT `knowledge_admin_actions` → 业务变更 → 必要的 outbox，三者原子。业务失败回滚成功动作与业务写入，再独立记录净化后的失败事件；留痕失败如实报告，不伪造失败事件已持久化。确认/发布使用预期对象版本，版本冲突返回 409；发布支持幂等键，重试不得重复产生 publication/outbox。

| 方法 | 语义 |
|---|---|
| `confirm_source_governance(source_id, *, source_version, expected_governance_version, ownership, use, audiences, validity, basis, context)` | 校验来源存在、未撤回且未到期 → admin action → 新 governance_version；重新治理按 §3.1 级联失效。原始来源行不动 |
| `publish_candidate(candidate_id, *, expected_version, use, audiences, valid_until, idempotency_key, basis, context)` | 准入：证据实际存在、非纯共现/纯模型自证、全部来源未失效/未过期、全部当前有效治理版本及 §3.1 授权交集（不因原始 unverified 永久禁止已完成合法验证的数据）。publications+全部来源治理关联+outbox 同事务写入。失败返回明确业务错误，不伪装成「缺另一人批准」，不伪造已发布 |
| `reject_candidate(candidate_id, *, basis, context)` | 拒绝置状态 + action 记录 |
| `revise_candidate(candidate_id, *, modifications, basis, context)` | 生成**新 candidate 版本**（derived_from 旧版）；旧证据不原位改写、不伪造来源 |
| `withdraw_source(source_id, *, source_version, basis, context)` | `invalidate_knowledge_source` 级联（tombstone/outbox/consumer_assets 失效），保留原始 ACL，入口绑 admin action |
| `revoke_publication(publication_id, *, basis, context)` | `revoke_transactional` 语义保留，steward 角色检查换 admin action 绑定 |

- admin 路径**禁用内存 dict 回退**（管理必须真 PG）；`KnowledgeLedger` 内存实现仅保留给 extractor/consumer 纯单测。
- 消费者保留幂等回执、资产应用与回执同事务、逐行 savepoint 及来源锁；授权依据改为 §3.1 的有效治理授权，不能继续要求业务受众命中 restricted-candidate 原始处理 ACL。B2 不把消费循环接入抽取 worker 主循环，但 T5 必须真实调用消费、导出和词典编译服务验证复用；B3 装配独立消费执行器及管理作业，不能在模型请求中驱动消费。

### 3.1 有效消费授权与多来源失效

- 原始来源 ACL、处理 ACL、治理消费授权、管理权限分别存储。管理员查看或登录不授予消费权；显式治理动作才产生版本化消费授权。新受众可在原始处理 ACL 之外获得合法消费授权，但不得超出服务端允许的部署范围和用途边界。
- 对候选全部贡献来源，发布受众必须是各有效治理版本消费受众交集的子集；发布用途必须被每个来源治理版本允许，不能继承仅用于采集处理的用途作为业务消费许可。空交集拒绝发布，不能默认为全域可用。
- 发布期限不得超过全部来源保留期限和治理版本期限的最小值。绑定精确来源版本与治理版本，消费者仍逐次验证来源未撤回、未到期、绑定治理版本未被替代及发布未撤销，不只相信缓存快照。
- 同一来源版本重新治理时，旧治理版本退出当前有效集合；依赖它的发布保守失效，不自动继承扩大后的受众或期限。替代治理、来源撤回、发布撤销与资产失效/outbox 同事务完成；到期由读取即时拦截，后台补充失效投递。重新使用需显式重新发布。
- 失效事件包含 publication、治理版本和资产谱系的稳定标识；重复投递幂等，乱序旧发布事件不得重新激活失效资产。无下游回执只能显示“失效待确认”，不能宣称全部副本已删除。

### 3.2 可用性展示契约（B2 后端冻结，B4 页面使用）

全状态查询仍供管理排障；可用性是服务端根据权威状态计算的独立结果，不由 candidate.state 或 publication 存在与否推断。列表和详情提供一致字段，支持状态、受众、用途、有效期限与来源筛选，稳定分页并限制页大小；未指定目标消费者/用途时返回 `not_evaluated`，不宣称所有受众均可用。

| 维度 | 返回字段与状态 | 判定依据 |
|---|---|---|
| 治理 | governance_status、blocking_reasons | 未确认/可发布/拒绝/已替代；全部来源与证据校验 |
| 消费资格 | eligibility、evaluated_consumer、evaluated_use、effective_audiences、effective_use、valid_until | eligible/ineligible/not_evaluated/unknown；有效授权交集、来源与发布生命周期 |
| 投递 | delivery_status、pending_event_count、last_attempt_at、last_error_code | not_dispatched/pending/applied/failed/invalidation_pending；outbox 与消费回执 |
| 复用资产 | consumer_id、asset_id、asset_version、asset_kind、receipt_id、applied_at、invalidation_status | 实际持久资产与回执；无资产时返回空集合，不伪造已复用 |
| 证据 | evidence_status | available/expired/destroyed/corrupted/key_unavailable/unknown；实际留存与密钥状态 |
| 采集时间 | evaluated_at、状态版本 | 标明快照时间；缺依赖不得将未知显示为可用 |

`blocking_reasons` 使用固定码，例如 `GOVERNANCE_MISSING`、`GOVERNANCE_SUPERSEDED`、`AUDIENCE_DENIED`、`PURPOSE_DENIED`、`SOURCE_EXPIRED`、`SOURCE_WITHDRAWN`、`PUBLICATION_REVOKED`、`EVIDENCE_UNAVAILABLE`；不回传内部 SQL、路径或密钥信息。消费者状态评估不等于授予读取权，实际消费仍执行授权读取。正文仅在详情显式读取，元数据列表不批量解密。

### 3.3 复用闭环与脱敏词典边界

B2 保证治理模型下的服务闭环：确认来源 → 发布 → outbox → 消费应用与回执 → 授权导出/词典编译 → 撤回或到期后阻止新使用。B3 提供正常部署下的消费作业、导出/编译 API 与资产版本查询；B4 页面分别显示发布、投递、消费和生效状态。B2 未装配消费执行器时必须显示 not_dispatched/pending，不能宣称部署已完成消费。

重复利用按 publication/consumer/用途/目标版本绑定稳定幂等键，保存实际资产版本、输入发布集合及来源治理谱系；同一有效知识可供多个获授权消费者独立使用，不重复修改原始证据。已有导出服务只输出获授权结构化事实，不导出原始提示词或恢复映射。

词典编译只生成候选资产，不直接改变在线检测器。B3 必须校验条目类型、冲突与检测效果，再通过完整保护包构建、验证、发布和回退；新请求采用新版本，在途请求保持原包。发布知识不能自动生成检测豁免、调整分类外发政策或恢复映射。词典输入失效后停止新编译与发布，查询标出已部署包受影响，B3 受管重建/回退阻止后续新请求继续使用失效条目；在途请求仍固定原包。资产失效与运行包已替换分别展示，不能仅凭 outbox 宣称在线版本已撤除。

## 4. 审计直接读取（`audit/admin_reader.py` 新文件）

### 4.1 可信审计目录

- state 下新目录 `audit-catalog`，durable_commit 原子写（沿用 `audit_intent` 模式，OS 锁+配额）。
- 受控后台目录构建器只扫描装配固定的 intent/evidence 根目录，从已持久化的可信 intent 取得 tenant/domain，验证证据 record_id、用途、格式版本、摘要及关联后原子追加 `CatalogEntry`。条目包括 tenant_id、record_id、purpose、domain、bucket、intent_id、受控根下相对 evidence_path、evidence_sha256、bytes、created_at、retention_until、生命周期政策版本及 status；保留期限来自服务端权威政策，不能根据客户端值补造。
- intent 与证据必须通过持久化的精确 record_id 关联，禁止根据时间邻近或文件排序猜测。若既有 intent 未保存该关联，T3/T4 在原有 intent 提交中增加服务端预分配的 evidence record_id 及生命周期引用，由既有 EvidenceSpec 使用同一标识；只扩展现有必需提交的可信元数据，不增加同步写入次数或目录依赖。对应 `audit_intent.py` 归 T3、pipeline 的元数据装配归 T4，门禁行为不变。
- B2 装配独立、限额的目录构建循环，按稳定记录标识幂等处理并可重启重扫；不在 `EvidenceGate.admit` 中新增目录落盘、排队等待或回调。没有可证明租户关联或生命周期依据的旧记录保持不可见，不由管理员任意导入路径恢复。
- **崩溃窗 fail-closed**：catalog 有而 evidence 缺失或 sha256 不符 → 条目按 corrupted 拒绝释放正文；evidence 有而 catalog 无 → 该记录对管理读不可见（不接收任意密文/路径）。
- 目录故障只影响目录新鲜度与管理读，不影响已经满足既有留证门禁的模型请求。路径解析拒绝根目录外路径与符号链接逃逸；实际读取校验当前文件、摘要与生命周期，不将目录 available 当作永远可读。目录构建结果与积压对管理可查，失败不伪造成功。

### 4.2 AdminReviewService

gateway 只注入 `FileKmsProvider`（与 history 共用 KEK 持有链，不自建 KMS）。

- `list_records(filters, cursor, context)`、`get_record(record_id, context)`：先验证租户/域范围，仅返回元数据。固定筛选、稳定游标及页大小上限；扫描和内存排序有预算，不全量解密或无界加载目录。
- `read_plaintext(record_id, context)`：验证会话、条目存在、租户/域匹配、未过期且未销毁 → **可靠记录访问尝试** → 校验摘要与 AAD（domain/purpose/record_id/格式版本，与 `envelope_crypto.build_aad` 一致）→ `decrypt_record` → 重新校验会话 → **可靠记录真实访问结果** → 再次校验会话与生命周期 → 释放单条明文。用途固定为允许的受控审阅用途；装配限定审计证据根和密钥权限，不接受知识域任意密文。
- 会话校验由服务注入受信 revalidate 回调，实际检查期限和持久注销状态；API 层释放前再调用 `auth_service.revalidate`。KMS、写盘耗时跨过截止时间均不返回明文；崩溃留下尝试无结果时显示 unknown，不伪造读取成功。
- 每次尝试与结果使用独立 durable_commit 文件，记录固定操作/结果码、actor、session_digest、记录句柄摘要、范围与时间，不含明文或密钥。留痕写失败返回 `AUDIT_WRITE_FAILED` 且不释放正文；失败事件写入本身失败时不宣称已落盘。存储成功的解密结果不等于正文已向客户端释放。

### 5.1 资源隔离与故障边界

- 管理 PG、目录构建、解密和消费各有有限并发、队列、超时及批量上限，不与检测/NER 共用工作队列；阻塞 SQL、KMS 和文件扫描不能占用 ASGI 事件循环。部署参数与默认限额在 T4 冻结，满载返回固定忙碌/依赖不可用状态。
- 审计目录和管理访问事件使用独立配额与存储预算，不能挤占必需 intent/evidence/spool 的保留空间；共享卷时配额及保留空间检查必须可证明，不能仅依赖目录名隔离。管理空间耗尽阻止相应管理动作；关键必需留证空间耗尽仍执行原安全门禁。
- 管理 PG 断连、旧 schema、目录不可写、消费积压和管理限流不改变检测、替换、还原、分类、BYOK 或保护包选择，不关闭检测或切到原文外发；复用资产只有受管发布成功才影响新请求。
- 该隔离承诺针对新增能力及其预算内负载，不承诺整机磁盘、共享 KMS 或操作系统完全故障时仍可外发。T5 同时证明新增故障隔离与既有门禁仍有效，避免用吞异常实现可用性。

### 8.1 授权、展示与复用验收

1. 合成 BYOK 来源的原始 ACL 仅含 restricted-candidate；admin 明确确认指定消费者和用途后，该消费者可真实消费，其他消费者及用途拒绝；登录本身不产生授权，原始 ACL/unverified 字段不变。
2. 两来源受众分别为 {采购, 法务} 与 {法务}，只能发布给法务；交集为空、任一治理版本缺失、来源错版/到期/撤回均拒绝。遗漏贡献来源不能提交，发布与重新治理/撤回并发不穿透授权。
3. 发布成功但未消费显示 pending/not_dispatched；仅在资产和回执同事务成功后显示 applied 与实际版本。依赖不可用显示 unknown 或能力错误；已撤回无下游回执显示 invalidation_pending，不显示全部删除。
4. 真实调用 consume_once、授权 JSONL 导出和词典编译，不以构造 publication ID 或内存 dict 代替复用；消费者重复执行不重复副作用，消费中途失败回滚资产与回执，乱序事件不复活失效资产。
5. 治理版本替代、受众缩小、来源撤回及到期后，旧发布/缓存快照不能用于新的读取、导出或编译；失效谱系、outbox 和回执可追踪。多个合法消费者独立复用同一知识，权限与资产版本不混用。
6. B3 追加正常部署的作业执行与词典保护包发布纵切：接受、编译、发布、生效分开；未校验/发布失败资产不影响检测，在途请求固定版本，撤回后运行包替换状态可查。B4 页面按同一后端事实验收，不提供假成功按钮。

### 8.2 脱敏不受新增能力干扰的验收

1. 对知识管理 PG 断连、指纹不符、目录写失败/积压、消费停机、管理队列饱和分别注入故障；两协议 JSON/SSE 的合法合成请求继续执行原检测、替换、外发与还原。审计能力按自身资源判定，不受知识 DSN 连带关闭。
2. 在配置限额内持续目录扫描、管理分页和正文解密负载，同时执行模型请求；验证事件循环及检测队列不被阻塞、管理配额不占用必需留证空间。冻结测试环境、并发、批量与耗时预算，对照关闭新增能力的基线验证，不用“结果正确”替代时延/资源检查。
3. 对模型检测结果、供应商所见脱敏载荷、客户端还原内容、保护包版本做确定性断言；管理操作不能改变检测策略、分类外发权限或在线恢复映射。检测门禁与部署显式失败政策保持既有语义。
4. 既有必需加密留证、历史持久化或 REQUIRED spool 失败时，仍按原契约阻止外发；共享 KMS 故障影响必需留证时不能伪称已隔离而放行。新增目录失败时证据保留，管理暂不可见，恢复后受控重扫建立目录。
5. 审阅覆盖可信租户关联、生命周期、路径逃逸、真实 AES-GCM、尝试/结果写失败、解密后及结果落盘后会话到期/注销；任何拒绝路径不返回正文，不把成功解密记录当作已释放明文。

## 9. 风险

1. **指纹常量与 DDL 漂移**：DDL 改了常量没更新 → 启动即拒。缓解：T1 测试强制「常量 = 真实元数据计算值」。
2. **T4 的 `app.py`/`start_gateway.py` 与 T5 读依赖**：顺序执行规避；冻结点在任务间固化接口。
3. **目录构建延迟与孤立证据**：证据先存在、目录后生成；管理显示真实积压，缺目录记录不可见，T3 验证重启重扫和损坏拒绝，不增加出口同步门禁。
4. **授权依据漂移**：消费若继续只检查原始处理 ACL，将出现已确认却不可用；若只检查单个治理版本，则可能多来源越权。T1/T2/T5 共同验证全部来源治理交集、版本替代及并发失效。
5. **复用交付与状态误报**：B2 服务验证不等于正常部署已消费；B3 必须装配真实执行器/作业和词典保护包发布，B4 使用实际回执及运行版本显示，禁止把发布、消费与生效合并为一个成功状态。
6. **共享资源争用**：进程、磁盘与 KMS 仍可能共享，目录名分离不能证明隔离；T4 明确限额与保留空间，T5 负载及故障注入证明新增能力不占用脱敏必需预算，既有安全门禁保持。
